# NetworkHelm в браузере: страница без шлюза

Веб-приложение бывает двух видов. Из [шлюза](../../server/README.ru.md) оно ходит к роутерам через сервер, который открывает за него TCP-, SSH- и UDP-соединения. Со статического хоста вроде GitHub Pages сервера за страницей нет: каждый запрос уходит из самого браузера. Это второй вид, его собирает `./gradlew :app:webApp:pagesBundle` в `app/webApp/build/pages`.

**English:** [README.md](README.md)

Страница узнаёт свой вид по `<meta name="networkhelm-mode" content="standalone">` в `index.html`: такой тег есть только в пакете для Pages. Сохранённые роутеры и настройки она кладёт в `localStorage` браузера, пароль держит до закрытия вкладки. В пакете есть манифест веб-приложения и service worker, поэтому браузер может установить страницу как приложение и открыть её без сети (файлы берутся из сети, пока она есть, и сохраняются).

## Демо-роутеры

При первом заходе в списке окна подключения лежат шесть роутеров, по одному на платформу:

| Хост | Платформа | Протокол |
| --- | --- | --- |
| `routeros.demo` | MikroTik RouterOS 7.24 | REST |
| `openwrt.demo` | OpenWrt 24.10 | ubus по HTTPS |
| `opnsense.demo` | OPNsense 25.1 | API |
| `pfsense.demo` | pfSense 2.8 | API |
| `vyos.demo` | VyOS 1.4 | HTTP API |
| `keenetic.demo` | Keenetic 4.3 | RCI |

Они живут в памяти страницы, открываются с любым паролем, и каждое подключение начинается с данных из `core/.../demo/`: что изменило одно подключение, следующее не найдёт. В списках работают добавление, изменение, удаление и перенос; Safe Mode демо-RouterOS откатывает изменения; ping, traceroute и трафик интерфейса отвечают строками. Адреса взяты из документационных диапазонов (192.0.2.0/24, 198.51.100.0/24, 203.0.113.0/24), MAC-адреса — 00:00:5E:00:53:xx, диапазон, который RFC 7042 отводит под примеры. У строк каждой платформы есть столбцы её паков, поэтому окна выглядят так же, как на настоящем устройстве; меню, для которых в демо нет данных, не показываются.

## Настоящие устройства

Страница отправляет HTTP драйверов через `fetch`, так что REST RouterOS, `/ubus` OpenWrt и API OPNsense, pfSense, VyOS и Keenetic идут так же, как из настольного приложения. Другое дело, что пропускает браузер, и о том, какое из ограничений сработало, он не говорит:

- **CORS.** Страница читает ответ другого источника, только если ответ это разрешает. REST RouterOS отвечает без `Access-Control-Allow-Origin`, а предварительный запрос браузера (его вызывают заголовки `Authorization` и `Content-Type: application/json`) получает `503`. Измерено на RouterOS 7.26 лабораторного роутера. `/ubus` OpenWrt 25.12 тоже отвечает без заголовка; пользователи пишут, что его включает `option ubus_cors '1'` в секции `main` файла `/etc/config/uhttpd`, на лаборатории это не пробовали. OPNsense, pfSense, VyOS и Keenetic не измеряли: таких устройств в лаборатории нет. Настройка `allow-origin` API VyOS относится к его GraphQL, а не к REST-вызовам, как сказано в баг-репорте VyOS 1.4.0. Обратный прокси, который отвечает на `OPTIONS` кодом `204` и добавляет к ответам `Access-Control-Allow-Origin`, `-Headers` и `-Methods`, делает любое из этих API читаемым.
- **Смешанное содержимое.** Pages отдаётся по HTTPS, поэтому страница не может запросить адрес с `http://`; исключение — `http://localhost` и `http://127.0.0.1`.
- **Сертификаты.** Сертификат устройства проверяет браузер, закрепить его отпечаток нельзя. Самоподписанный сертификат не проходит, пока этот же браузер не открыл адрес один раз и не принял предупреждение.
- **Локальная сеть.** Свежий Chrome спрашивает пользователя, прежде чем публичная страница обратится к адресу частной сети.

Устройство, к которому браузер не пустил, даёт одно сообщение с этими причинами. Различить их точнее нельзя: для `fetch` все они — один и тот же `TypeError`.

## Чего страница не может совсем

Это не HTTP, а ничего, кроме HTTP, браузер не посылает, как бы ни была отдана страница:

| Протокол | Для чего нужен |
| --- | --- |
| API и API-SSL RouterOS (8728, 8729) | бинарный API RouterOS |
| TCP 8291 | протокол WinBox |
| SSH, SFTP (22) | терминал, файлы, OpenWrt по SSH, Safe Mode RouterOS до 7.18 |
| MAC-Telnet, MNDP (UDP) | роутеры по MAC-адресу, список соседей |
| SNMP (UDP 161) | устройства, читаемые по SNMP |
| SSDP (UDP 1900) | поиск устройств UPnP |

В окне подключения страницы эти протоколы серые. Direct Sockets, API браузера для TCP и UDP, есть только у установленных Isolated Web Apps Chrome, у обычной страницы его нет. Через шлюз работает всё перечисленное: он открывает это со своего компьютера, и страница шлюза предлагает то, что шлюз сам о себе сказал.

## Публикация

`.github/workflows/deploy_pages.yml` собирает пакет и публикует его на GitHub Pages; его вызывает процесс выпуска, кроме предварительных версий, и прикладывает к выпуску `NetworkHelm-web-<версия>.zip`. Архив — тот же пакет: распакованный на любом статическом хосте по HTTPS (service worker требует его, `localhost` не в счёт), он даёт ту же страницу. В репозитории публикация Pages должна быть включена через GitHub Actions.

Пути в пакете относительные, поэтому страница работает и по адресу `https://<пользователь>.github.io/<репозиторий>/`.
